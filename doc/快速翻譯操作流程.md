# JPComedy 快速翻譯作業流程

這份文件是給之後協助柏文翻譯日本搞笑影片的 AI 操作手冊。目標是收到網址後，直接辨識影片、完成日文轉錄、繁中翻譯、字幕燒錄與驗證；只在必須確認付費或遇到阻礙時打斷柏文。

## 預設成品

- 收到日本綜藝、漫才或搞笑影片網址後，直接開始前置檢查；不再問「要不要開始」或要求使用者重述流程。
- 預設交付已燒錄繁體中文字幕的 MP4，並保留可編輯的 SRT、ASS 和原始素材。
- 字幕依使用者目前的固定偏好：白字、實心黑底、不加粗、正常置底。**不分析、不辨識、不因為畫面上的日文大字卡移動中文字幕**；除非使用者另行指定。
- 輸出沿用來源解析度與幀率，目標是在可接受畫質下縮小檔案。優先試用 HEVC（`libx265`、`medium`、CRF 27），但這只是試編碼起點，**不保證輸出比原片小**。實際編碼與大小必須依下方「燒錄與檔案大小驗收」確認。
- 柏文的成品大小目標：**約為實際輸入原片的 90～100%**，與原片差不多或略小；畫質良好且能更小時也可接受。原片大小是預設上限，不能默默交付明顯變大的影片。這是交付目標，不是保證重編碼能同時縮小又完全無損；必要時依下方流程提出具體畫質取捨。
- 版面設定以 GitHub 上 `allen365apple/JPComedy` 的 `preferences.json` 為準，不要假設本機檔案已同步。此設定曾與本機版本不同；讀取 GitHub 現行設定時只取與本次交付有關的欄位。

## 收到網址後的單一路徑

1. **辨識來源與既有工作**：讀取標題、影片 ID、時長、解析度及可用字幕；檢查 `projects/` 中是否已有相同影片 ID。已有專案就續跑，不重做完成的下載、ASR 或翻譯，也不覆蓋已存在的輸出檔。
2. **一次處理費用確認**：先估算 ElevenLabs Scribe v2 ASR 費用，並同時列出美元與台幣約數。翻譯使用本機已設定的 Codex 訂閱模型；若任何步驟會另外使用按量計費 API，將所有費用合併成一則確認訊息，只詢問一次。使用者尚未同意前，可以做免費的 metadata、快取和設定檢查，不可呼叫付費服務。遇到新增的費用或預算超過原同意上限時，再停下確認。
3. **取得日文逐字稿**：下載必要影音，取得平台官方字幕作為可選參考（若平台有提供），抽取音訊並用設定中的 ElevenLabs 日文 ASR 產生 `video.ja.srt`。重跑時沿用 ASR 快取，避免重複計費。
4. **翻譯與術語統一**：用節目標題、平台資訊、共享固定詞庫和字幕內容自動建立簡潔的單集 briefing；需要時再查證人物、組合及節目專名。先做全片脈絡分析，再使用 GrillMaster 分塊並行翻譯。沿用 `.pre_pass/`、`.chunks/` 等快取；不要為了「重新開始」清除或重做它們。
5. **只做必要品質檢查**：確認日文原稿與最終繁中 SRT 的字幕段數、索引及時間碼完全相符，沒有空白譯文；抽查開場、笑點回收、結尾及專名。依目前流程使用必要的 refine／詞庫校對；不做 OCR、逐格掃描或大規模畫面文字位置分析。
6. **套樣式並直接燒錄**：讀取 GitHub `preferences.json` 的現行字型、大小及邊界設定，產生固定置底黑底字幕；先依下方規則試編碼，再輸出一支全新的 MP4。檢查實際 FFmpeg 命令，不能只憑文件或副檔名判斷編碼。不要改寫原始影片、SRT 或既有成品。檔名用繁中主題名稱，並加清楚的「黑底字幕版」標記。
7. **完成後一次驗證與回報**：確認影片時長接近來源、解析度及幀率相同、影像和音訊串流存在，並讓 FFmpeg 完整掃過影片影格。依下方規則比較原片與成品大小。回報影片、SRT、ASS 的可點擊絕對路徑、實際編碼、解析度、原片／成品大小、大小變化比例、字幕段數與美元／台幣費用。長任務約每 10 分鐘或在階段完成時主動簡短回報，不要每幾十秒重複輪詢。

## 燒錄與檔案大小驗收

### 先區分目前程式與交付目標

檢查日期：2026-10-19。目前 `services/subtitle_burnin.py` 的 `render_saved_profile()` 仍使用 **H.264（`libx264`）、`veryfast`、CRF 18**，不是上面希望使用的 HEVC 設定。直接執行這個函式不代表已完成小檔案輸出；操作者必須檢查當前程式與實際命令，使用能明確指定編碼參數的燒錄路徑。

`preferences.json` 目前只保存字幕和 Podcast 版面欄位，沒有影片編碼器、CRF 或目標大小設定。讀取這份檔案不會自動改變壓縮方式。MP4 是容器，不能因為副檔名是 `.mp4` 就宣稱使用 HEVC。

### 操作與驗收順序

1. 用 `ffprobe` 記錄**實際燒錄輸入檔**的時長、解析度、幀率、影音編碼、位元率與檔案位元組數。不要拿另一個下載中間檔或平台估算大小代替輸入檔比較。若探測工具無法執行，先處理工具問題，不能回報「已驗證」。
2. 從原片挑有動作、複雜背景及字幕的代表片段，先試編碼並檢查畫質、字幕可讀性與耗時。避免先跑整集才發現設定錯誤。HEVC 可從 `libx265 medium CRF 27` 開始；CRF 是品質控制，沒有檔案大小上限。不同編碼器的 CRF 數字也不能直接比較。
3. 原音訊可直接放入 MP4 時優先沿用（`-c:a copy`），減少不必要的音訊重編碼。需要轉換時明確記錄音訊格式與位元率。字幕燒錄需要重編影像，不能對影像使用 stream copy。
4. 若試編碼顯示輸出可能膨脹，先調整設定與比較畫質。預設以原片大小的 95% 作為計算起點，驗收目標為 90～100%；採目標位元率與兩次編碼控制大小時，總位元率預算約為「目標 MB × 8,000 ÷ 秒數」（kb/s），再扣除音訊及容器餘裕。大小和畫質有取捨，不承諾在任意原片上同時做到更小與無損。不要為了湊數字降低原解析度或幀率。
5. 全片完成後，以 `ffprobe` 核對實際編碼、時長、解析度與幀率，並比較位元組數。大小統一以十進位 MB（1 MB＝1,000,000 bytes）回報，避免與 MiB 混用。大小變化＝（成品 bytes ÷ 原片 bytes − 1）× 100%。
6. **成品若比輸入原片大，不可直接標示為「壓縮完成」交付。** 先嘗試合理的更小版本並抽查畫質；若必須明顯犧牲畫質才能符合大小目標，提供具體的大小／畫質結果給使用者選擇。所有試片、舊成品與原片都保留，新的輸出使用新檔名。

若使用 VideoToolbox 硬體編碼，需另外測試大小和畫質，不能沿用 `libx265` 的品質參數推定結果。最終記錄實際執行命令、工具版本、驗證結果與大小比較，讓下一次能重現。

## 不得省略的安全規則

- 不得刪除、覆寫、移動原片、字幕、快取、舊版影片或任何其他檔案。需要新輸出時使用新的檔名／資料夾。
- `services/package/core.py` 的包裝流程會在目標資料夾已存在時先遞迴清除它。**不可對既有目標直接執行 package**；如果要使用該流程，必須先選一個全新的、不存在的目標路徑，並確認不會碰到使用者資料。
- 不讀出、不回顯、不寫入文件或 Git 的 API Key、cookies、密碼；檢查 `.env` 只回報必要設定是否存在或已設定。
- 不因影片下載失敗就嘗試繞過存取控制。說明問題，改用使用者有權提供的本機素材。
- 不推送或部署公開內容，除非使用者明確要求；公開前先掃描金鑰、私人路徑、個資與內部資訊。

## 這次流程的改進結論

「感情好到太誇張」一集的工作原片為 96,228,999 bytes（96.23 MB），黑底字幕成品為 213,869,707 bytes（213.87 MB），約為原片的 2.22 倍。這表示只確認有輸出影片，沒有驗收檔案大小，不符合小檔案交付目標。

先前版本把預期的 HEVC 設定寫成已完成的編碼／驗證結果，欠缺可追溯的實際命令與探測紀錄；該說法已移除。現有燒錄函式的預設也不能證明每支歷史成品的實際編碼。之後必須以輸出檔探測與日誌為準，不把文件中的目標設定當作完成證據；也不再為日文畫面大字卡跑 OCR。
