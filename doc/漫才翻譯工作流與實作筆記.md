# 日本綜藝與漫才影片翻譯：工作流與實作筆記

這份文件記錄 Owarai GrillMaster 實際處理日本綜藝、漫才比賽與長篇影片時，
形成的一套可重複工作流。目標不是綁定單一模型，而是把語音辨識、翻譯、
時間軸驗證、詞庫管理與交付整理成可續跑、可檢查的製作流程。

## 先說結論：GPT‑5.6 能不能直接完成翻譯？

可以負責核心的語言工作，但不等於可以捨棄整套工具。

- **GPT‑5.6／Codex 是翻譯的大腦**：理解上下文、辨認ボケ與ツッコミ、處理雙關、
  統一人物語氣、修正 ASR 誤聽，並根據字幕與影格做推理。
- **GrillMaster 是製作管線**：下載或讀入影片、抽音軌、呼叫 ASR、保留時間碼、
  分段、續跑、檢查 SRT 結構、產生 ASS、套用詞庫並整理成品。
- **視覺化詞庫是長期記憶**：把組合名、成員名、節目名與漫才術語變成可重複
  使用的規則，不必每支影片重新提醒模型。

短片或少量字幕可以直接貼給模型翻譯；一整集節目若要求字幕不漏行、時間軸
正確、失敗後可續跑，仍然需要 GrillMaster 這類確定性的管線。最實用的使用方式
是把 Codex 當操作介面，由它在背景使用 GrillMaster，而不是每次手動執行每個步驟。

## 支援的輸入

### 線上影片

將網站網址直接作為 `SOURCE`。目前流程可處理 yt-dlp 支援的來源，並額外處理
AcFun 分 P 網址。例如：

```bash
grill "https://www.acfun.cn/v/ac00000000_2" "節目名稱與集數提示"
```

網站的登入狀態、地區限制或反爬機制可能需要 `cookies.txt`。請只處理自己有權
下載及使用的內容。

### 本機影片

把影片檔案路徑作為 `SOURCE`：

```bash
grill "/path/to/video.mp4" "節目名稱、播出年份、出演者或段子提示"
```

處理狀態與中間結果會放在 `projects/<id>/`。此資料夾已由 `.gitignore` 排除，
不應提交影片、音訊、字幕或模型回應到 GitHub。

## 完整處理流程

```text
網址或本機影片
  → 取得／整理影片
  → FFmpeg 抽取日文音訊
  → ElevenLabs Scribe v2 語音辨識與時間碼
  → 產生日文 SRT
  → Pre-pass 全片分析人物、專名、語氣與段落
  → 分塊翻譯（字幕＋局部摘要＋影格）
  → 結構驗證與重新對齊
  → 可選的語句潤飾與固定詞彙校對
  → 輸出繁中 SRT 與 ASS
  → 可選的影片封裝／燒錄
```

### 1. 影片與音訊

線上來源先以 yt-dlp 取得影音，本機來源則直接匯入。下載畫質可透過
`DOWNLOAD_MAX_HEIGHT=720` 等設定限制，避免沒有必要的儲存與處理成本。
FFmpeg 會把聲音轉成適合 ASR 的單聲道音訊。

### 2. ASR 語音辨識

ElevenLabs Scribe v2 負責把多人快速對話轉成帶時間碼的日文字幕。這一步與翻譯
分開的好處是：翻譯模型可以更換，時間軸仍有穩定來源。

ASR 仍可能誤聽：

- 組合名、人名、地名或節目名
- 同音異字與關西腔
- 觀眾笑聲、掌聲蓋住的句子
- 漫才中刻意含糊、模仿口音或唱歌的段落

因此後面仍要利用上下文、影格與詞庫修正。

### 3. Pre-pass 全片分析

不要直接逐句翻譯。先讓模型看完整字幕、節目資訊與代表影格，建立：

- 出演者、組合與角色關係
- 本集專有名詞和 ASR 修正表
- ボケ／ツッコミ的分工與說話語氣
- 雙關、回收伏筆與固定譯法
- 各段摘要，供後續 chunk 保留全局脈絡

這一步能避免同一人名前後譯法不同，也能減少只看局部句子而錯失笑點。

### 4. 分塊翻譯

長片依字幕字元數切成多個 chunk，平行處理。每塊收到原始字幕、pre-pass 摘要、
該段影格；支援音訊的 backend 還可收到音訊切片。切塊結果會快取，失敗時可從
已完成部分續跑。

漫才翻譯的優先順序建議是：

1. 不改字幕 index 與 timecode。
2. 忠實傳達前提、誤會與笑點的回收關係。
3. 使用自然、簡潔、能在畫面停留時間內讀完的繁體中文。
4. 保留必要的日本文化資訊，但避免每句都加生硬註解。
5. 人名、組合名、節目名與術語以固定詞庫為準。

### 5. 結構驗證、潤飾與名詞校對

生成式模型可能漏 index、重複區塊或改動時間碼。GrillMaster 會先做本機結構
檢查；可安全對齊時直接修復，否則再交給 agent 依原文恢復結構。之後可選擇：

- `refine`：改善繁中口吻、笑點節奏與閱讀長度。
- `glossary-check`：檢查殘留日文、英文名稱與固定譯名。

這兩階段不應擅自增加原文沒有的資訊，也不應破壞字幕數量與時間軸。

### 6. SRT、ASS 與影片

- **SRT**：相容性最好，包含時間碼與純文字，適合播放器與後續校對。
- **ASS**：可設定字型、位置、描邊、顏色與多種樣式，適合正式觀看或燒錄。
- **封裝／燒錄影片**：把字幕固定在畫面上，播放最方便，但之後無法關閉字幕。

建議保留 SRT 與 ASS；需要跨裝置直接播放時，再另做燒錄版影片。

## 視覺化詞庫管理

macOS 可雙擊專案根目錄的 `開啟漫才詞庫管理.command`。也可以在專案目錄執行：

```bash
.venv/bin/python -m glossary_ui.server
```

瀏覽器開啟 <http://127.0.0.1:8765> 後，可以：

- 搜尋組合、成員、節目或術語
- 修改日文別名與繁中固定譯名
- 新增備註，記錄年份、角色或翻譯理由
- 封存與還原暫時不用的項目
- 輸入一段日文，預覽正式翻譯流程會命中哪些詞條

正式資料位於 `services/fixed_glossary/fixed_glossary.json`。介面儲存時會先在
`services/fixed_glossary/backups/` 建立本機備份；備份資料夾不納入 Git。

詞庫修改的原則：

- 優先收錄會反覆出現、模型容易誤譯的名稱。
- `jp` 可放漢字、假名、簡稱等多個別名。
- `zh` 應維持單一、穩定的繁中寫法。
- `note` 用來記錄辨識線索，不要放 API Key 或私人資料。
- 有歧義的普通詞不要過度收錄，以免誤命中。

若只是某一支影片的特殊背景，優先使用命令列的 `TRANSLATION_HINT`；只有跨影片
都要沿用的名稱，才適合加入固定詞庫。

## Prompt 應包含的漫才知識

模型需要的不只是「翻成繁體中文」，還應明確知道：

- 判斷ボケ、ツッコミ、前振り、天丼、被せ、ノリツッコミ等結構。
- 前提與誤會若要在後段回收，前段譯文不能提前解釋或破梗。
- 吐槽通常要短、快、口語；不要直譯成冗長書面語。
- 雙關無法直譯時，先保留情節功能，再選擇自然的中文笑點；必要時用極短註記。
- 不確定的人名或作品名應先查證或標記，不要憑空音譯。
- 不要把觀眾笑聲當成台詞，也不要為了流暢而合併不同時間碼。

跨影片的穩定規則適合放在 skill、AGENTS.md 或固定 prompt；單集資訊放在
`TRANSLATION_HINT` 與 pre-pass，避免把一次性內容永久塞進全局規則。

## 模型選擇的實際經驗

模型不是越新就必然在每個環節都最好，應分開看能力：

- GPT‑5.6／Codex 適合語意推理、繁中潤飾、結構修復、詞彙校對與操作本機流程。
- 能直接接收音訊的模型，在唱歌、口音或 ASR 不確定處可能多一層線索。
- 即使翻譯品質很好，模型輸出的 SRT 結構仍必須由程式驗證。
- API 的 429、503 或模型 404 通常是配額、服務壓力或模型可用性問題，與 prompt
  品質無關。流程應保留重試、切換 backend 與快取續跑能力。

若某個雲端模型不穩定，實務上可將 pre-pass、chunk、postprocess 分別指定不同
backend。使用 Codex 訂閱執行 GPT‑5.6 時，仍要另外計算 ElevenLabs ASR 等外部
服務費用；任何付費 API 都應先確認額度與預算。

## 安全與 GitHub 發布

可以公開程式、測試、範例設定與去識別化的流程文件，但提交前必須確認：

- `.env`、API Key、Token、cookies 不在 Git 追蹤範圍。
- `projects/`、下載影片、音訊、字幕與模型原始回應不會被提交。
- 本機絕對路徑、使用者名稱與私人資料已移除。
- 詞庫只包含公開藝人、節目及一般術語，沒有私人客戶或內部資料。
- `services/fixed_glossary/backups/` 僅留在本機。

建議公開前先檢查 Git diff，再用關鍵字掃描準備提交的檔案。Fork 同步時，保留
原作者 repository 作為 upstream，將自己的 fork 作為推送目標，避免誤推到上游。

## 最後形成的操作習慣

1. 先給來源與節目提示，不急著手動拆字幕。
2. 付費 ASR 或 API 執行前先確認預估費用與上限。
3. 讓流程保留每階段產物，錯誤時續跑，不重付已完成步驟的費用。
4. 先看較長、具代表性的段落再比較模型，不用過短片段下結論。
5. 成品同一資料夾保留繁中命名的影片、SRT、ASS，方便搬移與整理。
6. 翻譯中發現固定名稱問題，就回到視覺化詞庫修正，讓下一支影片自動受益。

這套方法的核心不是「永遠使用某個模型」，而是把模型放進一條可驗證、可替換、
可持續累積詞彙知識的流程中。
